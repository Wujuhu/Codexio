# 压缩历史与请求归档

Mac／Windows 开发版当前为 0.3.12。原始 Codex 文件只读，开发包分别在本机 Mac 和 Windows 主机构建、验证。

## 正式数据与缓存

- `usage_records`、请求归属和计价依据继续保存在原账本中。来源暂时不可见、文件被压缩或清理读取缓存都不删除已确认记录。
- `usage_request_archives` 在同一个账本中长期保存请求的完整正文、最终回复和已有明细元数据。每行采用标准 zlib 流（`zlib-json-v1`），保存解压长度、SHA-256、业务内容摘要和版本；读取校验长度及摘要。归档与对应账本／消息更新使用同一 SQLite 事务。
- `usage_request_messages` 仅为可淘汰的明文热缓存。原有 512 条／64 MiB 预算保留，但只允许淘汰已有同版本归档的行；超出热缓存预算的单条明细直接从归档读取，不截断后保存。清空热缓存后仍能恢复正文。
- 成功采集的内嵌图片以原有 PNG／JPEG 等格式，按内容哈希去重保存到数据目录下的 `request-history-media`。预览缓存和临时解压目录可以清理，正式归档与这些图片不属于缓存。外部附件仍保留原始引用；原日志未包含且已经丢失的外部文件不能凭空恢复。
- 已读取的执行行程页也压缩归档，缓存键包含请求、分页位置和实际来源签名；展示时仍使用当前账本的计价结果。

## 读取与完整性

`RolloutFile.swift` 和 `rollout_file.go` 复用已有解析器需要的可定位读取接口。Zstandard 解码采用有界输入／输出缓冲，将一个源文件解码到临时文件，完整校验通过后才交给解析器。同一源的并发读取共用临时文件；最后一个读取者关闭后立即清理，异常退出遗留的本程序缓存会在后续使用时清理。没有 1 GiB 的总解压文件截止条件，磁盘空间不足会报错并保留已经确认的历史。

源文件的身份、大小、修改时间以及解析／归档版本共同决定是否需要处理。上次处理已经完成且依赖未变时，后续轮询直接复用结果，不重新解压。扫描中的检查点和成功完成标志分开；中断时继续未完成工作，不能因文件属性未变而跳过尚未处理的后半段。

正文恢复不再止于文件前 64 MiB。已有账本的旧正文缓存先迁入归档；对先前已索引但尚未完整归档的来源，补做一次正文归档，不重新累计 Token。新采集的正文在解析时直接归档。有效的末尾 JSON 记录即使没有最后一个换行符也会处理。来源变化继续使用原有游标、记录身份、分组、去重和完整替换校正机制。

## 实现复用

- 原有 `Database.writeRequestMessage`／`saveMessage` 的内容摘要、消息版本和按需恢复是归档入口；摘要不因访问时间变化。
- 文件身份、前缀／尾部检查点和增量采集沿用现有 Mac／Go 实现及 v0.2.10 机制。
- Zstandard 解码继续使用官方 v1.5.7 解码器与 Go `klauspost/compress v1.20.3`；请求明细压缩复用系统 zlib 与 Go `compress/zlib`，两端归档编码一致。
- 常规验证仍为原有三项隔离冒烟。大文件末尾读取、清缓存后恢复和未变化来源复用的核对只针对本次问题，结果保存于 `build/checks`，不新增维护性测试套件。

## Windows 启动读取

桌面启动只打开账本、读取已有派生版本和轻量设置；首次投影准备由已有后台采集器执行。主写连接与工作锁保留，界面查询使用最多两个只读 WAL 连接，读取上一次已提交的物化视图，事务提交后由已有 generation 通知更新。写入和正文恢复仍通过原写连接，取消上下文同时传到读、写连接。

首屏不再等待手机同步、上游服务和报告状态；这些完整设置在概览首次返回后补齐。服务初始化离开原生窗口事件线程，启动与退出共用生命周期锁，退出时先取消上下文，避免延后执行的初始化重新开启服务。无数据或首次升级时仍保留真实加载状态，不以空数据冒充已完成。

## 子代理继承边界修复

部分旧子代理日志中的 `subagent_history_start_ordinal` 来自继承上下文，但子代理自己的日志序号会重新从零开始。仅按 `ordinal < boundary` 判断会误跳过分叉之后的新计量及请求配置。

Mac／Windows 沿用已有继承判断，并在分叉时间之后优先采用明确的本线程归属；新的本地 turn_context／任务开始记录建立当前子线程的后续事件归属。分叉之前的上下文以及明确属于其他线程的记录继续走原有继承和去重规则。回补保留原 response／rollout／请求身份，不把自动审批审查当作新的主用户请求。

旧游标仅在带有正数继承边界且 `ownership_version` 过旧时，对对应的已索引来源重新解析一次。其余未变化日志继续复用原结果。修复版本随游标检查点保存，中断可续读，完成后不反复解压或重扫。账本中的完整正文归档与已确认历史仍保留。能恢复 Token 但项目已确认的价格目录没有对应内部型号时，费用继续显示 `—`，不套用其他模型的价格。

活动页按各自配置的本机来源统计。单台设备恢复现存压缩日志不等于汇总其他设备、云端或已丢失来源的完整历史；逐日覆盖必须同时核对原始记录、账本及实际使用入口。

## 所有用户的自动发现与保留

这些机制属于 Mac／Windows 的正常采集流程，不依赖某台电脑、账户、会话 ID 或一次性修复脚本。首次安装会读取配置的 Codex 数据目录（默认 `CODEX_HOME`／用户的 `.codex`），以后继续增量采集。除 `sessions`／`archived_sessions` 目录外，也复用原生 `state*.sqlite` 的 `threads.rollout_path`，发现数据目录内原生数据库明确引用的旧日志；仅将路径作为只读文件线索，目录标题或线程总数不生成 Token、费用和用户请求。主库与 WAL 均参与变化检查，未变化不重新查询；文件不存在时保留已确认账本。正文恢复与执行行程使用相同的数据目录路径范围和 `.jsonl`／`.jsonl.zst` 读取机制。

Windows 对文件替换、截断、内容改写或压缩表示交接时未再次出现的旧来源贡献，持久标记为 `retained`；后续强制刷新与应用重启也不按缺项删除。相同调用 ID、请求 ID 再次出现时仍复用原来的更新与去重规则，未变化来源仍直接跳过。解析规则修复仍可校正同一来源中当前可确认的记录，不把“新文件没有这一行”当作历史用量被撤销的证据。Mac 原有账本写入即保留未再次出现的旧记录。

两端在重读旧日志时保留已有的明确模型、主消息归属、完成状态与已观测事实。不完整正文即使带有不同的消息键，也不得覆盖已完整归档的正文；正文、消息身份和对应附件作为一组保留，后续确实完整的新消息仍可正常更新。明文热缓存的清理不影响压缩归档。

官方的 rollout 文件压缩与模型上下文精简是不同操作。现存 `.jsonl.zst` 可以无损解码恢复其中仍有的计量和正文；若原始内容在 Codexio 首次采集之前已被删除或只剩摘要，无法凭空恢复。Codexio 主程序运行时持续保存已采集内容；主程序退出后不会另建独立采集服务，也无法保证在未运行期间抢先归档被上游删除的内容。
