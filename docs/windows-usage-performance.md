# Windows 用量页读取优化（0.3.12）

2026-10-29，本机 Windows 的活动页打开时，原 `GetTrends` 会顺序计算概要、趋势图、模型明细、聊天排行与活动统计。排行组件挂载后还会独立请求排行。首次活动页因此等待不可见内容，详情页也附带了完整活动与排行计算。

0.3.12 按 `Query.view` 只读取活动、详情或排行的当前标签，页面尚无对应数据时保留加载提示；标签与 Agent 切换沿用原取消和序列保护。执行行程在活动结果可用后挂载，避免空 generation 与实际 generation 各读一次。日志筛选列表只在日志页需要时获取。

汇总复用 v0.2.10 `usage_queries.py::_metrics` 与当前 `usage_priced_calls.metrics` 的投影机制。概要、图表、模型和活动统计合并已经校验过的逐调用计量数据，保留缺失指标、有效计数、用户请求分类及补偿求和规则；不重复解码完整请求元数据。旧 Python 形状的 metrics 在后台升级完成前从原记录计算，避免启动显示空统计。模型对应的用户请求数由一次分组查询取得，保留原 EXISTS 的去重含义。账本、价格变化依旧使既有 generation 缓存失效；价格调整只重算已有索引，不重新解压历史。

## 一次性隔离测量

Windows 主机 WJH，使用真实账本的 SQLite 只读备份：全账本共 14,106 条计量记录、2,007 条主用户请求；本次计时选择 Codex，其中包含 11,944 条计量记录、1,512 条主用户请求，时间范围 2026-04-13 至 2026-10-29。期间不启动或重启用户已安装应用，不执行采集与重新计价。两版查询读取同一静态副本；每组创建新服务清空进程内查询缓存，未清空操作系统文件缓存。旧版基于本地提交 `f2169e3`，新版为本次 0.3.12 源码。

| 后台读取 | 修改前首次查询 | 修改后首次查询 | 修改后缓存命中 |
| --- | ---: | ---: | ---: |
| 活动页 | 2396.555 ms | 745.459 ms | 1.999 ms |
| 详情页，全部范围 | 4907.888 ms | 1362.669 ms | 1.505 ms |

同一账本的活动统计、365 天活动数据、详情汇总、图表和模型明细逐项相同（浮点比较容差 1e-9 绝对值／1e-12 相对值）。计价规则更新前的投影用于性能等价比较；Terra Ultra Fast 的新增计价单独核验。

结果来自一次问题定位测量，不是维护性测试套件，也不扩展现有三项隔离冒烟。它衡量服务层返回数据的耗时，不包含窗口创建、WebView 绘制、后台首次历史回补及整机 CPU／内存／能耗。原始记录位于 `build/staging/windows-usage-0312`，正式交付校验位于 `build/checks`。

## Mac 同类路径检查

Mac Codex 的 `UsageView` 只创建当前标签；活动使用 `UsageSnapshotCache` 的后台快照，详情使用按 revision／筛选条件缓存的 `AsyncProjection<TrendProjection>`，排行从 `LocalChatRankingStore` 有界读取 25 条。因此没有 Windows 原先在每次打开活动页时串行读取全部三个标签的路径。

检查发现并移除两处冗余：`Analytics.build` 仍生成无消费者的旧 `localChatRows` 排序数组，随后快照缓存又立即清空它；实际排行早已使用 SQLite 物化索引。删除旧数组的累加和排序，保留真实排行索引与执行行程索引。另外，`ClaudeUsageView` 原先在任意用量标签挂载或 Claude revision 变化时查询完整活动统计；改为仅活动标签可见时计算，切回活动时通过既有 revision 缓存加载最新值。

Mac 结论来自代码路径审计和此次重新打包的三项隔离冒烟；未把 Windows 的耗时结果推广为 Mac 的性能提升比例。
